## 2. Findings

### EBW-001 — CRITICAL — There is no authentication, and the guard is what removes it

`src/app/core/session/auth.guard.ts:16-22`

```ts
if (!session.isAuthenticated()) {
  session.signIn('staff@ebpco.gov.ph');
}
```

The route guard **creates a session when one is absent** instead of refusing entry.
`SessionService.signIn()` (`session.service.ts:43`) unconditionally issues
`role: 'Super Admin'`. Net effect: typing any admin URL into the address bar grants
full Super Admin access to Applications, Payments, Permit Release, Users & Roles,
Workflow and System Logs. Sign-out is undone by the next navigation.

The role registry in `permissions.ts` is careful, correct and well-argued work —
and it is **entirely unreachable**, because the only role the app ever issues is
the one that passes every check.

### EBW-002 — CRITICAL — Login never checks the password

`src/app/pages/login/login.ts:46-63`. `onSubmit` validates that `email` matches
`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, then calls `session.signIn(normalized)` and navigates.
`this.password` is read from the form and **never used**. Any syntactically valid
email plus any password is a successful Super Admin login.

### EBW-003 — HIGH — `setRole()` is a live privilege-escalation backdoor

`session.service.ts:52`. A public method on a root-provided service that rewrites the
current session's role in place. Any script on the page can call it. It is documented
as "mock-only", which is not an access control.

*(The owner's local line already deleted this method — see §3.)*

### EBW-004 — HIGH — Nothing in either app talks to a server

Measured: `grep -rn "HttpClient|provideHttpClient|fetch(|XMLHttpRequest|axios"` over the
Angular `src/` → **zero hits**. `pubspec.yaml` declares **no `http` and no `dio`**;
the Flutter app's only `dart:io` uses are local file/photo handling.

Both surfaces are in-memory prototypes. Every application, evaluation, assessment,
payment, receipt, permit and audit event is generated at load by a seeded PRNG
(`application-seed.ts:27`, `mulberry32`) and vanishes on refresh. Nothing entered here
is recorded anywhere.

### EBW-005 — HIGH — Registration is a dead end

`src/app/pages/register/register.ts`. Validates the fields, then
`this.router.navigateByUrl('/login')`. No account is created, no store is touched,
no password rule beyond "the two boxes match". A user who registers and then tries
their new credentials gets in — but only because EBW-002 lets everyone in.

### EBW-013 — INFO — `bypassSecurityTrustResourceUrl` is safe today, fragile tomorrow

permit-form iframe URL. Verified safe **as written**: the URL comes from a constant
lookup table and is `encodeURIComponent`-wrapped (`permit-form-templates.ts:30-33`).
It stops being safe the moment that URL comes from a server response — which is exactly
what EBW-004's fix will do. Flag it now so the bypass gets revisited with the API work.

## 3. The one-line verdict

**The build is healthy and the code is thoughtful. The product has no authentication,
no server, and two forks of itself drifting apart.**

Toolchain, bundle discipline, test coverage and the reasoning in the comments are all
above average. What is missing is not quality — it is the entire back half of the system,
plus a decision about which of the two front-end lines is the real one.

## 4. Recommended order

1. **Decide which line is canonical** (EBW-006/007) — this blocks everything else and
   gets more expensive daily.
2. **Fix the guard** (EBW-001) — one function; make it redirect instead of sign in.
   Then EBW-002/003/005 follow from having a real session.
3. Point the canonical line at `ebpco-api` (EBW-004), revisiting EBW-013 as you go.
4. Repo hygiene: license/visibility decision (EBW-008), root `.gitignore` + a CI job
   that runs the 284 tests already written (EBW-009), then the dead weight
   (EBW-010/011/012).
